# ADR 0001: Sonos-to-Jellyfin audio playback

- Status: Accepted
- Date: 2026-09-15
- Task: 8.1
- Compatibility baseline: Sonos SMAPI 1.1 and Jellyfin Server 10.11.11

## Context

Sonofin must resolve a Sonos track ID into audio that a Sonos player can fetch
from Jellyfin. The intended data path is:

```text
Sonos player -- getMediaURI --> Sonofin SMAPI Worker
Sonofin      -- PlaybackInfo --> Jellyfin API
Sonos player -- GET/HEAD/Range + Authorization --> Jellyfin audio endpoint
```

The Worker performs authentication and playback negotiation, but it does not
fetch, buffer, transform, or proxy audio. Sonos documents that stream requests
go directly from the player to the media server, that custom `httpHeaders` are
sent verbatim, and that the stream must support accurate content lengths and
byte ranges. Sonos can also repeat `getMediaURI` during one playback session
and expects the returned URI not to change.

Jellyfin 10.11.11 returns client-influenced `MediaSourceInfo` objects. Two
fields cross an important trust boundary:

- `TranscodingUrl` is an arbitrary string generated by Jellyfin. In 10.11.11
  it normally contains the usable Jellyfin access token in an `ApiKey` query
  parameter.
- `RequiredHttpHeaders` is an arbitrary string dictionary used by Jellyfin for
  some underlying remote sources. It is not the client-to-Jellyfin
  authentication contract.

Neither field is safe to return to Sonos without validation. This ADR fixes the
contract for Tasks 8.3 and 8.4. Task 8.1 itself adds no playback route and does
not make tracks playable.

The source-level Jellyfin decisions below are pinned to 10.11.11, the version
used by the current real-system evidence. Supporting another Jellyfin major
version requires rechecking its playback negotiation, URL generation, and
authorization source before claiming compatibility.

## Decision

### 1. Playback topology and trust boundary

`getMediaURI` will return one fully qualified HTTPS Jellyfin URL and one
internally constructed `Authorization` header. The Sonos player then connects
directly to Jellyfin.

Sonofin will not add any of the following in the initial implementation:

- a Cloudflare audio proxy;
- a Sonofin download or range endpoint;
- a custom signed media URL;
- an access token, Sonos credential, or other credential in a query string;
- redirects as part of the expected playback path;
- DRM fields or a `deviceSessionToken`.

The deployed playback path is HTTPS-only even though the Jellyfin client has a
separate explicit insecure-HTTP option for local development. A media target
that cannot satisfy this contract is rejected rather than downgraded.

`getMediaURI` and `getMediaMetadata` are independent operations. Neither may
depend on the other having run first.

### 2. Sonos `getMediaURI` contract

The request body follows WSDL order: required `id`, then optional `action`,
`secondsSinceExplicit`, and `deviceSessionToken`. `id` must be one canonical
Sonofin track ID and also satisfy the stricter 128-character limit documented
on the Sonos reference page.

The initial service capability does not opt in to implicit/explicit playback
actions or DRM. If Sonos nevertheless supplies an optional field, the parser
bounds and validates it but source selection does not use it. A
`deviceSessionToken` is opaque Sonos DRM context, never Jellyfin authentication.
Raw action, token, zone-player, playback, and item identifiers are not logged.

The full WSDL response order is `getMediaURIResult`, optional
`deviceSessionToken`, `deviceSessionKey`, `contentKey` or `contentKeys`,
`httpHeaders`, `uriTimeout`, `positionInformation`, and
`privateDataFieldName`. The initial response emits only
`getMediaURIResult` followed by `httpHeaders`; omitted optional elements do not
change that order. Each `httpHeader` contains `header` followed by `value`.
Task 8.4 must XML-escape both the URI and header data exactly once.

Because the URLs defined below are deterministic, Sonofin does not initially
need mutable state keyed by `X-Sonos-Playback-Id` to honor Sonos's stable-URI
requirement.

### 3. Jellyfin negotiation request

Sonofin will call `POST /Items/{itemId}/PlaybackInfo` with an explicit JSON
body. It will not rely on Jellyfin's defaults or obsolete query parameters.

The resolver will repeat the profile checks locally rather than trusting the
server flags alone. Missing required stream facts cause that candidate to be
transcoded or rejected; Sonofin does not guess.

The one fallback output is progressive HTTP MP3, stereo, at most 48 kHz and
320 kbps, with CBR requested. HLS is outside the initial contract. This avoids
manifest/segment credential propagation and supplies one deterministic MIME
type.

Jellyfin 10.11.11 disables its distinct HTTP direct-stream path in
`MediaInfoHelper`. Sonofin therefore disables direct stream in the request and
does not synthesize a direct-stream URL. A source that is not direct-playable
must produce a validated MP3 `TranscodingUrl`; from Sonofin's perspective that
is the `transcode` method even if Jellyfin can internally remux or copy part of
the input. A future Jellyfin version may add a real `direct-stream` method only
after a new source and hardware compatibility decision.

### 4. Source and audio-stream selection

Only a response negotiated with the profile above is eligible. Sonofin will:

1. Reject a top-level `ErrorCode`, an empty source list, or malformed response.
2. Validate every source independently and discard invalid candidates without
   exposing the rejected value.
3. Identify the audio stream using `DefaultAudioStreamIndex`; otherwise accept
   exactly one `IsDefault` audio stream; otherwise accept a sole audio stream.
   Multiple ambiguous streams reject that source.
4. Rank valid direct-play candidates before valid transcode candidates, `File`
   sources before other protocols, and source ID as the final stable tie-break.
5. Pin the selected source ID in the media URL. A response flag is never enough
   by itself: container, codec, stream limits, URL, headers, and MIME must all
   pass local validation.

Initial direct play accepts `File` protocol only. `Path` is never returned,
logged, or used as a public URL. A non-file or remote source can still play
only if Jellyfin supplies a conforming same-origin MP3 transcode target.

### 5. Direct-play URL construction

Jellyfin does not return a direct-play URL. Sonofin will construct this stable
application-relative endpoint from the configured server URL, not from
`MediaSourceInfo.Path`:

```text
/Audio/{percent-encoded itemId}/stream.{container}
  ?static=true
  &mediaSourceId={percent-encoded sourceId}
```

The extension is the one validated container: `mp3`, `aac`, `m4a`, `mp4`, or
`flac`. Query keys are serialized in the fixed order shown. The connection's
Jellyfin base path is preserved. No `PlaySessionId`, device ID, user ID, token,
or API key is necessary for static audio, so none is placed in the URL.

### 6. Transcode URL normalization

`TranscodingUrl` is parsed as hostile input. It is never concatenated directly
into XML. A valid target must meet all of these rules:

- It is either an application-root-relative Jellyfin path or an absolute HTTPS
  URL on the exact configured origin, including port.
- Jellyfin's generated leading `/audio/...` path is interpreted relative to
  the configured Jellyfin application base path. A path already containing the
  base path is not prefixed twice. An absolute URL must already be beneath that
  base-path boundary.
- User information, a fragment, a scheme-relative URL, dot-segment or encoded
  traversal, encoded path separators, an alternate origin, and a base-path
  escape are rejected.
- The normalized path is exactly
  `/audio/{expected itemId}/stream.mp3` beneath the base path. The selected
  source ID, MP3 codec, progressive `http` subprotocol, and reported transcode
  container must agree.
- Query names are unique and case-exact. After credential removal, only the
  parameters produced by the accepted Sonofin profile are allowed:
  `DeviceId`, `MediaSourceId`, `AudioCodec`, `AudioStreamIndex`,
  `AudioBitrate`, `AudioSampleRate`, `TranscodingMaxAudioChannels`,
  `EstimateContentLength`, `RequireAvc`, `EnableAudioVbrEncoding`,
  `mp3-audiochannels`, `allowAudioStreamCopy`, `allowVideoStreamCopy`, and
  `TranscodeReasons`. Values receive field-specific bounds and enum checks.
  Unknown keys reject the candidate.
- One canonical `ApiKey` may be present only because Jellyfin 10.11.11 creates
  it. Its decoded value must equal the connection token, after which it is
  discarded before a target exists. Duplicate `ApiKey`, lowercase `api_key`,
  `token`, `access_token`, `authorization`, `key`, or any other
  credential-like query key rejects the candidate. Raw query text and values
  are never logged.
- `PlaySessionId` and `Tag`, when returned, are validated and discarded. They
  are optional at Jellyfin's audio endpoint and would otherwise make repeated
  `getMediaURI` results change. Remaining parameters are emitted once in a
  canonical order using fresh percent-encoding.

If later hardware evidence shows that Jellyfin requires `PlaySessionId`, the
replacement design must reuse a negotiated target for the Sonos playback
session using hashed identifiers. It must not fall back to exposing a query
credential or minting a Sonofin-signed media URL.

### 7. HTTP header policy

The allow-list for values copied from `RequiredHttpHeaders` is empty. A source
with a non-empty map is ineligible. Those headers describe access to an
underlying source and are not proof that Sonos should send them to Jellyfin.

The only emitted stream header is:

```text
Authorization: MediaBrowser Client="Sonofin", Device="Cloudflare Worker", DeviceId="<percent-encoded connection device id>", Version="0.0.0", Token="<percent-encoded connection token>"
```

It is constructed from the already validated, decrypted connection using the
same encoder as Jellyfin API requests. It is not copied from PlaybackInfo. With
one fixed header, output ordering is deterministic.

Sonofin never emits or forwards `Cookie`, `Host`, `Range`, `Content-Length`,
`Transfer-Encoding`, `Connection`, `TE`, `Trailer`, `Upgrade`, `Keep-Alive`,
`Proxy-*`, `Forwarded`, `X-Forwarded-*`, a returned `Authorization`, or any
other header. Sonos owns its `Range` header. All names and values are bounded;
control characters, NUL, CR, or LF reject the candidate.

Task 8.5 must verify that real Sonos firmware sends the supplied
`Authorization` header on ordinary, ranged, and any `HEAD` requests. The Sonos
documentation explicitly guarantees GET passthrough but does not explicitly
guarantee identical behavior for HEAD.

### 8. Container, codec, and MIME policy

The playback target uses this exact map:

| Method | Container | Codec | Required limits | MIME |
| --- | --- | --- | --- | --- |
| direct play | `mp3` | `mp3` | mono/stereo, at most 48 kHz | `audio/mpeg` |
| direct play | `aac` | `aac` | mono/stereo, at most 48 kHz | `audio/aac` |
| direct play | `m4a` or `mp4` | `aac` | mono/stereo, at most 48 kHz | `audio/mp4` |
| direct play | `flac` | `flac` | mono/stereo, at most 48 kHz, at most 16-bit | `audio/flac` |
| transcode | `mp3` | `mp3` | mono/stereo, at most 48 kHz, at most 320 kbps | `audio/mpeg` |

Container and codec comparisons are ASCII case-insensitive after accepting one
bounded token. A missing, comma-separated, unknown, or conflicting value is
rejected. MIME is derived from this table only, never from an arbitrary
response string or URL suffix.

Sonos also recommends FLAC frames no larger than 32 KB. PlaybackInfo does not
expose enough information to prove that property, so the resolver cannot
enforce it. The checked-in FLAC fixture represents qualifying media and Task
8.5 must verify the real FLAC file and hardware result. Failure moves that file
to transcode; it does not relax the limit silently.

The Jellyfin HTTP response's `Content-Type` must match the selected target MIME.
The existing catalog metadata MIME remains a description of the source item;
Sonos states that the actual stream format is determined from the content type
at the media URI. The forced-transcode case is therefore an explicit Task 8.5
compatibility gate.

### 9. Failure, stability, and observability

A bad candidate is skipped. If no candidate remains, Tasks 8.3 and 8.4 will
return a fixed credential-safe no-compatible-stream failure and map it to a
fixed Sonos server fault. They will not return the rejected URL or header,
retry with a query token, proxy the stream, or weaken same-origin checks.

Direct targets are deterministic by construction. Transcode targets become
deterministic by dropping request-specific fields and canonicalizing the safe
query. Repeating resolution for the same item, source, profile, and connection
must produce byte-identical URL and ordered headers.

Logs may contain only closed classifications such as playback method and
failure origin. They must not contain raw or normalized URLs, query strings,
item/source/session/device/user/household IDs, header names or values,
PlaybackInfo bodies, access tokens, or rejected upstream text.

## Fixtures

The four JSON files under
`packages/jellyfin-client/test/fixtures/playback/` are full sanitized
PlaybackInfo responses for:

- MP3 direct play;
- AAC-in-M4A direct play;
- 16-bit FLAC direct play;
- 24-bit/96-kHz FLAC negotiated to progressive MP3.

All IDs and the transcode `ApiKey` marker are synthetic. The transcode fixture
deliberately retains one conspicuously fake `ApiKey` so Task 8.3 can prove that
the raw Jellyfin field is stripped; it is not a usable credential. The fixtures
contain no server URL, filesystem path, account data, or returned header.

## Consequences

- Jellyfin authentication reaches a user-owned Sonos player as an HTTP header,
  but not through a URL, log, fixture, or Cloudflare audio hop.
- Initial playback is intentionally limited to a small, auditable format set
  and one fallback output.
- Remote sources that require client-supplied headers and unsupported
  containers fail closed or transcode through Jellyfin.
- A Jellyfin upgrade can break the exact transcode query allow-list. That is an
  intentional compatibility failure requiring source review, not a reason to
  accept new query fields automatically.
- Successful unit fixtures are not a hardware claim. Range behavior, HEAD
  authentication, redirects, content length, MIME agreement, transcoder seek
  behavior, and repeated-session stability remain Task 8.5 gates.
